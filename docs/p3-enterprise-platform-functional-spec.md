# P3 제조 지식그래프 QA·RCA 엔터프라이즈 플랫폼 통합 기능명세

## 1. 문서 목적

이 문서는 다음 세 범위를 하나의 목표 명세로 통합한다.

1. 비스텔리전스 멘토링 주제 발표자료 6~7페이지에 명시된 프로젝트 3 필수 구현
2. 삼성전자·SK하이닉스 같은 반도체 기업과 타 산업 기업의 사내 플랫폼으로 확장하기 위한 제품형 UI·운영 기능
3. 발표자료 8~9페이지의 프로젝트 4에서 P3에 차용할 Agentic AI 기능

기능의 현재 구현 여부와 관계없이 최종 목표를 정의하며, 실제 구현 순서는
[`p3-enterprise-platform-implementation-plan.md`](./p3-enterprise-platform-implementation-plan.md)에서 관리한다.

## 2. 범위와 우선순위

| 구분 | 의미 | 완료 판단 |
|---|---|---|
| P3 필수 | 발표자료 6~7페이지 과제 충족 | 누락 시 프로젝트 3 미완성 |
| 엔터프라이즈 기능 기반 | 다중 프로젝트·다중 도메인 업무 기능과 운영 기반 | 기능 계약·백엔드·평가 기준으로 검증 |
| P3 사용자 서비스 완성 | 하나의 제품 UI에서 핵심 RCA 여정을 혼선 없이 완결 | 실제 사용자 브라우저 여정과 배포 UI Gate로 검증 |
| P4 차용 | 라우팅·Tool·HITL·감사로그·RAG·권고·알림 | P3 사용자 서비스 완성 후 별도 확장 |

중요한 경계:

- 새 파일 업로드나 새 Neo4j 연결만으로 새 프로젝트가 완성되는 것은 아니다.
- 새 도메인은 데이터 프로파일, 스키마·매핑 승인, 적재 무결성 검증,
  도메인별 Gold 질의셋과 프롬프트 준비를 거친 뒤 `ready` 상태가 되어야 한다.
- “타 도메인 재적용 가능”의 최소 조건은 코드에 고정된 스키마를 설정·Registry로
  교체할 수 있는 구조다.
- 이를 제품으로 증명하려면 프로젝트 생성·데이터 연결·진행상태·승인·평가·전환 UI까지 필요하다.
- 상용 서비스 수준은 UI만으로 달성되지 않는다. 인증, 권한, 데이터 격리,
  비밀정보 관리, 감사로그, 백그라운드 작업, 장애 복구가 함께 필요하다.
- 최종 사용자에게 제공하는 제품 UI와 개발·평가·운영 콘솔을 구분한다.
  동일 기능을 두 프론트엔드에 중복 구현해 서로 다른 사용자 경험을 제공하지 않는다.
- 테스트·CI·HTTP 200·예외 0건만으로 사용자 서비스 완료를 선언하지 않는다.
  보이는 모든 내비게이션과 핵심 행동을 실제 브라우저에서 조작하고,
  의미 있는 본문·상태·다음 행동이 표시되는지 검증해야 한다.
- P3 사용자 서비스 완료 Gate를 통과하기 전에는 P4 차용 기능을 기본 사용자
  여정에 병합하지 않는다.

## 3. P3 필수 기능

### 모듈 1. 데이터 분석 및 그래프 스키마 설계

- **FR-1.1** 공개 제조 공정 데이터셋의 엔티티·속성·관계 구조를 분석한다.
- **FR-1.2** 노드 라벨, 관계 타입, 속성, 식별자, 카디널리티를 포함한 그래프 스키마를 정의한다.
- **FR-1.3** RCA·품질 추적·공정 영향분석 질문을 먼저 정의하고,
  “이 스키마로 이 질문에 답할 수 있는가”를 역으로 검증한다.
- **FR-1.4** 데이터 사전, 스키마 다이어그램, 관계 방향, 식별자 정책,
  결측·중복·고아 데이터 정책을 문서화한다.
- **FR-1.5** 스키마 변경 이력과 버전을 관리한다.

완료 기준:

- 최소 3개의 대표 업무 질문을 수동 Cypher로 정확히 답할 수 있다.
- 스키마의 모든 노드·관계·속성에 데이터 출처와 의미가 기록되어 있다.
- RCA 결과를 인과 확정이 아닌 관계 기반 원인 후보로 표현한다.

### 모듈 2. 그래프 적재 파이프라인(ETL)

- **FR-2.1** 원본 데이터의 결측치, 타입 불일치, 중복, 비정상 식별자를 정제한다.
- **FR-2.2** 정제 데이터를 노드·관계 레코드로 변환한다.
- **FR-2.3** Neo4j에 배치 또는 벌크 방식으로 대량 적재한다.
- **FR-2.4** 원본 레코드 수와 적재 노드·관계 수, 고아 노드,
  끊어진 참조, 필수 속성 누락을 검증한다.
- **FR-2.5** 재실행 시 중복 노드·관계가 생성되지 않도록 멱등성을 보장한다.
- **FR-2.6** 원본 파일 해시, 실행자, 실행 시각, 처리량, 오류,
  격리 레코드를 ETL 실행 기록으로 보존한다.
- **FR-2.7** 적재 전 dry-run과 적재 후 검증을 분리한다.

완료 기준:

- 빈 데이터베이스에서 한 명령 또는 한 작업으로 동일 그래프를 재생성한다.
- 동일 입력 재적재 후 불필요한 노드·관계 증가가 0건이다.
- 적재 실패 시 프로젝트가 `ready`로 전환되지 않는다.
- 실패한 레코드를 폐기하지 않고 원인과 함께 격리한다.

### 모듈 3. 질의 시나리오 및 평가 기준셋

- **FR-3.1** 도메인 전문가 관점의 대표 업무 질문 15~20개를 정의한다.
- **FR-3.2** 질문별 정답 Cypher와 실행 결과 스냅샷을 확보한다.
- **FR-3.3** 정상 질문뿐 아니라 빈 결과, 없는 엔티티, 모호한 질문,
  쓰기 요청, 잘못된 도메인 질문을 포함한다.
- **FR-3.4** Gold 질의셋을 Text-to-Cypher 성능 평가 기준선으로 사용한다.
- **FR-3.5** 스키마 버전과 Gold 질의셋 버전을 연결한다.
- **FR-3.6** Gold와 겹치지 않는 Blind 질문셋을 별도로 유지한다.

평가지표:

| 평가 대상 | 필수 지표 |
|---|---|
| Text-to-Cypher | 실행 성공률, 의미 결과 정확도, 엄격 계약 정확도 |
| 안전성 | 스키마 준수율, READ 전용 준수율, 빈 결과 처리율 |
| 자기수정 | 최초 실패 건수, 수정 시도율, 수정 성공률 |
| 질문 상태 분류 | Precision, Recall, F1, 혼동행렬 |
| 도메인 라우터 | Top-1 정확도, Top-k Recall, 거절·확인 정확도 |
| 최종 답변·권고 | 전문가 타당성, 근거 충분성, 과잉 확신 여부 |

Precision·Recall·F1과 혼동행렬은 Cypher 문자열 생성 자체보다
질문 의도·상태·도메인 분류 평가에 적합하다. Cypher는 문자열 동일성보다
실행 결과의 의미적 일치를 우선 평가한다.

### 모듈 4. Text-to-Cypher 파이프라인

- **FR-4.1** 선택된 프로젝트의 그래프 스키마를 프롬프트 컨텍스트로 주입한다.
- **FR-4.2** 자연어 질문을 Cypher로 생성한다.
- **FR-4.3** 생성 Cypher를 READ 전용으로 제한하고 쓰기 절·다중 statement를 차단한다.
- **FR-4.4** `EXPLAIN`으로 문법·스키마 오류를 실행 전에 검증한다.
- **FR-4.5** 오류 메시지를 모델에 피드백하여 제한된 자기수정 루프를 실행한다.
- **FR-4.6** 재검증을 통과한 쿼리만 실행한다.
- **FR-4.7** 빈 결과, 차단, 실패, 확인 필요 상태를 구분한다.
- **FR-4.8** 최종 결과와 함께 사용한 스키마 버전, Cypher, 검증 이력을 반환한다.
- **FR-4.9** 프로젝트별 프롬프트·few-shot·Gold 질의셋을 분리한다.

표준 상태:

- `success`
- `empty`
- `blocked`
- `failed`
- `needs_clarification`
- `unsupported`

### 모듈 5. 사용자 질의 UI

P3 필수 기능은 특정 프론트엔드 프레임워크가 아니라 사용자에게 제공되는
질의·근거 확인 기능으로 정의한다. 현재 제품 기본 구현은 React이며,
Streamlit은 같은 백엔드 계약을 사용하는 내부 진단 콘솔로 한정한다.

- **FR-5.1** 자연어 질문 입력 인터페이스를 제공한다.
- **FR-5.2** 생성된 Cypher를 표시한다.
- **FR-5.3** 조회 결과를 표와 근거 경로로 표시한다.
- **FR-5.4** 조회 결과에 근거한 자연어 답변을 표시한다.
- **FR-5.5** 질문·답변·Cypher·결과·경로·검증 이력이 한 흐름에서 연결되어야 한다.
- **FR-5.6** 빈 결과·차단·실패·확인 필요 상태를 사용자가 구분할 수 있게 표시한다.
- **FR-5.7** 프로젝트별 대화 기록과 질문 재실행을 지원한다.
- **FR-5.8** 최종 사용자 제품 UI와 내부 진단 콘솔의 책임을 분리한다.
- **FR-5.9** 제품 UI의 모든 표시 내비게이션은 의미 있는 본문과 행동으로 연결되어야 한다.

### 모듈 6. 결과보고

- **FR-6.1** Gold·Blind 질의셋 기준 정확도 평가 리포트를 작성한다.
- **FR-6.2** 최종 발표자료를 작성한다.
- **FR-6.3** 스키마 문서, ETL 코드, 평가 결과, 실행 가이드,
  코드 저장소를 산출물로 정리한다.
- **FR-6.4** 문제-원인-해결-재검증 형식으로 Trouble Shooting을 기록한다.
- **FR-6.5** 모델·데이터·평가·보안 한계를 별도 문서로 공개한다.

### P3 비기능 요구사항

- **NFR-1** Neo4j Community 또는 Aura Free에서 핵심 기능이 동작한다.
- **NFR-2** Git/GitHub로 버전 관리한다.
- **NFR-3** 스키마, ETL·적재, Text-to-Cypher, UI·평가의 모듈 소유권이 명확해야 한다.
- **NFR-4** 비밀정보와 접속정보를 저장소에 커밋하지 않는다.
- **NFR-5** 테스트·평가·실행 방법이 재현 가능해야 한다.

### 발표자료에 명시된 활용 가치

- 관계형 모델과 그래프 모델의 차이를 비교하고 모델 선택 기준을 학습한다.
- 스키마 변경 시 코드 전체를 다시 작성하지 않고 프롬프트 컨텍스트와
  프로젝트 설정을 갱신하는 확장 구조를 구현한다.
- 품질 추적, 특정 ID의 원인 경로 탐색, 공정 변경 영향분석에 적용한다.
- 사내 지식그래프 기반 자연어 질의응답 시스템 프로토타입으로 확장한다.
- 동일 파이프라인을 설비 이력, 자재 이력 등 다른 그래프에 재적용한다.

## 4. 다중 프로젝트·다중 도메인 플랫폼 요구사항

### 4.1 프로젝트와 데이터 소스

- **FR-P-1** 사용자는 새 프로젝트를 생성하고 이름, 설명, 산업,
  도메인, 보안 등급, 담당자를 등록할 수 있어야 한다.
- **FR-P-2** 프로젝트마다 다음 데이터 소스 중 하나 이상을 연결할 수 있어야 한다.
  - CSV·JSON·XLSX·ZIP 업로드
  - 이미 구축된 Neo4j 접속정보
  - 향후 관계형 DB·Object Storage 커넥터
- **FR-P-3** 프로젝트마다 데이터 소스, 스키마, 프롬프트, Gold 질의셋,
  평가 결과, 대화, 감사로그를 분리한다.
- **FR-P-4** 사용자는 명시적으로 프로젝트를 선택하고 전환할 수 있어야 한다.
- **FR-P-5** 프로젝트는 `draft → profiling → mapping_review → loading →
  validating → evaluation_required → ready → failed/archived` 상태를 가진다.

### 4.2 데이터 온보딩 Wizard

```text
프로젝트 생성
→ 파일 업로드 또는 Neo4j 연결
→ 데이터 프로파일링
→ 노드·관계 후보 제안
→ 사용자 매핑 검토·승인
→ ETL dry-run
→ Neo4j 적재
→ 무결성 검증
→ 스키마 컨텍스트 생성
→ Gold 질의셋 작성·검증
→ 프로젝트 활성화
```

- **FR-P-6** 각 단계의 상태, 진행률, 처리 행 수, 예상·경과 시간,
  경고·오류를 화면에 표시한다.
- **FR-P-7** 오래 걸리는 작업은 백그라운드 Job으로 실행하고
  새로고침 후에도 상태를 복원한다.
- **FR-P-8** 작업 취소·재시도·실패 구간 재개를 지원한다.
- **FR-P-9** 스키마 자동 추론 결과는 사람 승인 전까지 적재에 사용하지 않는다.
- **FR-P-10** 기존 Neo4j 연결은 스키마 introspection과 샘플 질의 검증을 거친다.
- **FR-P-11** 새 프로젝트가 `ready`가 되기 전 자유 질의를 차단하거나
  제한된 미리보기 모드만 제공한다.

### 4.3 프로젝트 Registry

프로젝트 Registry는 최소 다음 정보를 관리한다.

| 영역 | 필드 예시 |
|---|---|
| 프로젝트 | `project_id`, 이름, 설명, 산업, 도메인, 소유자, 상태 |
| 데이터 | 소스 유형, 파일 해시, 연결 ID, 업로드·적재 실행 ID |
| 그래프 | Neo4j database/namespace, schema version, node/relationship counts |
| Agent | provider, model, prompt version, few-shot version |
| 평가 | Gold version, Blind version, 최근 평가 결과, readiness |
| 보안 | 접근 역할, 데이터 등급, 쓰기 권한 |

### 4.4 프로젝트 격리

- 프로젝트 간 노드·관계·질의·대화·평가·감사로그가 섞이지 않아야 한다.
- `project_id` 속성 필터는 데모 격리 수단으로 사용할 수 있지만,
  실제 서비스에서는 Neo4j database 분리, 별도 인스턴스, DB 권한 또는
  정책 기반 멀티테넌시를 사용한다.
- 현재 정규식 기반 `_has_project_scope` 검사는 발표용 방어선으로는 유효하지만,
  우회 가능성이 있으므로 엔터프라이즈 보안 경계로 간주하지 않는다.

### 4.5 프로젝트 준비 상태

프로젝트는 다음 조건을 모두 충족할 때만 `ready`로 활성화한다.

- 승인된 스키마와 매핑이 존재한다.
- ETL 또는 외부 DB 연결 검증이 성공했다.
- 무결성 검증이 성공했다.
- 스키마 컨텍스트가 생성되었다.
- 최소 Gold 질문이 작성·실행되었다.
- 읽기 전용·쓰기 차단 검증을 통과했다.
- 최근 평가와 데이터 버전이 연결되어 있다.

### 5.3 제품형 UX 요구사항

- 질문 결과는 다른 탭에 숨기지 않고 답변 직하에서 Cypher·결과표·경로를 확인한다.
- 사용자는 현재 프로젝트·데이터 버전·스키마 버전을 항상 확인할 수 있다.
- 프로젝트 전환 시 대화·필터·평가 컨텍스트를 안전하게 교체한다.
- 데이터 작업은 skeleton, 단계별 progress, 로그, 성공·경고·실패 상태를 제공한다.
- 그래프는 pan, zoom, drag, select, search, neighborhood expand,
  layout switch, property panel을 지원한다.
- 대화 기록은 프로젝트별로 저장·검색·재실행할 수 있어야 한다.
- 운영자는 적재·평가·오류·비용·응답시간을 한 화면에서 확인한다.
- 반응형, 키보드 접근성, 색상 대비, 한국어·영어 확장성을 고려한다.

### 5.4 엔터프라이즈 비기능 요구사항

- 사내 SSO/OIDC 연동 가능한 인증 경계
- 역할 기반 권한: Viewer, Analyst, Domain Expert, Data Steward, Admin
- 연결 비밀정보 암호화·Vault 연동
- 프로젝트·조직별 데이터 격리
- 전송·저장 암호화
- 감사로그 변경 불가 또는 append-only 저장
- 비동기 Job queue, 재시도, 취소, 재개
- API rate limit, timeout, circuit breaker
- 관측성: 로그, 지표, trace, 모델 호출비용
- 백업·복구·보존·삭제 정책
- 개발·검증·운영 환경 분리와 CI/CD

### 5.5 배포 프로필과 개발 기능 격리

런타임은 최소 다음 프로필을 구분한다.

| 프로필 | 목적 | 허용 기능 |
|---|---|---|
| `production` | 최종 사용자 서비스 | 승인된 제품 화면과 사용자 기능만 노출 |
| `demo` | 발표·포트폴리오 시연 | 고정 데이터·추천 질문 사용 가능, 개발 설명은 비노출 |

- **FR-UI-5.1** provider와 모델 선택은 서버 설정 또는 내부 Admin 기능으로

- **FR-UI-5.2** `OPENAI_API_KEY` 존재 여부, Gemini fallback, 실제 transport와

- **FR-UI-5.3** Gold Question은 Evaluations의 회귀평가 자산으로 유지하되,

- **FR-UI-5.4** 역할 미리보기·권한 시뮬레이션은 development에서만 허용한다.
- **FR-UI-5.5** `Stage 3-6`, `foundation`, `구현 준비`처럼 개발계획을 설명하는

- **FR-UI-5.6** 미구현 화면은 일반 사용자 내비게이션에서 숨기며,
  빈 껍데기 화면을 배포하지 않는다.

### 5.6 핵심 RCA 사용자 여정

제품 UI의 기준 여정은 다음 하나로 고정한다.

```text
프로젝트 선택
→ 자연어 RCA 질문 입력
→ 실행·검증 상태 확인
→ 자연어 답변과 결과표 확인
→ 생성 Cypher와 안전 검증 확인
→ 관계 경로·노드 근거 탐색
→ 결과 저장 또는 권한 있는 전문가 검토
→ 프로젝트별 History에서 재열기
```

- **FR-UI-6.1** 프로젝트 이름은 축약되더라도 전체 값을 확인할 수 있어야 한다.
- **FR-UI-6.2** 질문 결과의 기본 시선 순서는 답변 → 결과표 → 관계 근거 →
  Cypher·검증 상세로 구성한다.
- **FR-UI-6.3** `success`, `empty`, `blocked`, `failed`,
  `needs_clarification`은 서로 다른 제목·설명·다음 행동을 제공한다.
- **FR-UI-6.4** 쓰기 요청은 실행하지 않았다는 사실과 차단 이유를 명확히 표시한다.
- **FR-UI-6.5** 사용자는 같은 결과의 답변·표·그래프·Cypher가 서로 연결된
  근거 표현임을 이해할 수 있어야 한다.
- **FR-UI-6.6** 전문가 검토 기능은 권한 있는 역할에만 표시하고,
  일반 사용자에게는 검토 상태만 읽기 전용으로 제공한다.
- **FR-UI-6.7** 한국어 또는 영어 한 언어를 화면 단위로 일관되게 사용하며,
  부분 번역 상태를 정식 다국어 지원으로 표현하지 않는다.

### 5.7 실제 사용자 기준 Release Gate

사용자 서비스 완료는 다음 기준을 모두 통과해야 한다.

- 제품 진입점과 기본 내비게이션이 하나다.
- 화면에 보이는 모든 링크·버튼·메뉴를 실제 브라우저에서 조작한다.
- 모든 내비게이션 대상에 제목, 본문, 상태 또는 다음 행동이 존재한다.
- 클릭 후 흰 빈 화면, 중복 내비게이션, 프레임워크 내부 파일명이 나타나지 않는다.
- production·demo 화면에 개발·평가 전용 문구가 나타나지 않는다.
- 프로젝트 전환 후 URL·헤더·데이터·대화 컨텍스트가 일치한다.
- 대표 RCA 질문, 빈 결과, 쓰기 차단, 실패, 확인 필요 여정을 검증한다.
- 390px, 768px, 1280px, 1440px에서 핵심 행동이 가능하고 가로 overflow가 없다.
- 긴 프로젝트명, 긴 질문, 긴 결과와 빈 상태를 포함한 시각 회귀를 통과한다.
- 키보드 탐색, focus 표시, 명도 대비와 기본 접근성 검사를 통과한다.
- HTTP 200·exception 0건뿐 아니라 의미 있는 본문과 사용자 행동 결과를 검증한다.

이 Gate가 실패하면 P3 사용자 서비스는 `NOT READY`이며,
P4 Agentic AI 기능의 기본 사용자 여정 병합을 금지한다.

## 6. P4에서 P3로 차용할 Agentic AI 기능

### 6.1 자연어 기반 프로젝트 라우터

특정 프로젝트를 사용자가 선택한 경우 자동 라우팅을 끈다. 프로젝트를
선택하지 않은 메인 질의 화면에서만 LangGraph 라우터를 실행한다.

```text
질문
→ 등록 프로젝트·스키마 요약 검색
→ 의도·도메인 분류
→ 신뢰도 높음: 대상 프로젝트의 Agent 실행
→ 신뢰도 낮음/복수 후보: needs_clarification
→ 사용자가 확인하면 해당 프로젝트 컨텍스트로 재개
```

요구사항:

- 프로젝트 설명과 schema context를 대상으로 후보를 검색한다.
- `resolved_project_id`, confidence, 후보 목록, 라우팅 근거를 상태에 기록한다.
- 잘못된 분류를 감지할 수 있도록 사용자에게 선택 프로젝트를 표시한다.
- 낮은 신뢰도에서는 임의 실행하지 않고 확인 질문을 반환한다.
- 라우터 Top-1 정확도, Top-k Recall, 거절·확인 정확도를 평가한다.

### 6.2 Tool Registry

Text-to-Cypher를 하나의 긴 체인이 아니라 명시적인 Tool 집합으로 분리한다.

- `project_search_tool`
- `schema_lookup_tool`
- `query_graph_tool`
- `graph_rca_tool`
- `search_docs_tool`
- `recommend_action_tool`
- `etl_status_tool`
- `evaluation_tool`
- `request_approval_tool`
- `notify_tool`
- 선택: `text2sql_tool`, `anomaly_detection_tool`

각 Tool은 이름, 목적, 입력·출력 스키마, 권한, timeout, 오류 유형,
재시도 정책, 감사 필드를 가져야 한다.

### 6.3 문서 RAG 결합

- 공정 스펙, 품질 기준, 설비 매뉴얼, SOP를 문서 지식으로 적재한다.
- 그래프는 “무슨 데이터가 연결되어 있는가”를 제공하고,
  RAG는 “이 코드·기준·절차가 무엇을 의미하는가”를 제공한다.
- 답변에서 그래프 근거와 문서 근거를 분리해 표시한다.
- 문서 출처, 페이지·청크, 버전을 보존한다.
- 그래프 결과가 없는 경우 문서 근거만으로 제조 사실을 만들어내지 않는다.

### 6.4 조치 권고

- RCA 조회 결과와 승인된 SOP·문서 근거를 바탕으로 권장 조치를 생성한다.
- 권고는 원인 확정이나 자동 공정 제어가 아니라 검토 후보로 표현한다.
- 근거, 위험도, 우선순위, 담당 역할, 다음 확인 항목을 포함한다.
- 심각도·불확실성 기준을 넘으면 HITL로 전환한다.

### 6.5 HITL Interrupt

- LangGraph Interrupt로 실행을 중단하고 승인 대기 상태를 영속화한다.
- 승인·반려·수정 요청 후 같은 실행을 재개한다.
- 적용 대상:
  - 자동 추론한 스키마·매핑 승인
  - Neo4j 적재·스키마 변경
  - 심각도가 높은 조치 권고
  - 외부 알림 발송
  - 낮은 신뢰도의 프로젝트 라우팅
- 일반 READ 질의는 승인 없이 실행한다.

### 6.6 알림 발송

- 심각 이상, 승인 요청, 적재 실패, 평가 성능 저하를 webhook으로 전송한다.
- Slack, Teams, 이메일, n8n은 공통 `notify_tool` 뒤의 adapter로 분리한다.
- 알림 본문에는 프로젝트, 이벤트, 심각도, 근거 링크, 승인 링크를 포함한다.
- 중복 발송 방지 키, rate limit, 재시도, 발송 결과를 기록한다.

### 6.7 통합 감사로그와 상태 관리

질문부터 답변·권고·승인·알림까지 하나의 `run_id`로 연결한다.

최소 감사 이벤트:

- 사용자·프로젝트·질문
- 라우팅 후보·선택·신뢰도
- 사용한 스키마·프롬프트·모델 버전
- 호출한 Tool과 입력·출력 요약
- 생성·수정·실행한 Cypher
- 검증·자기수정 이력
- 결과 행 수·근거 ID·결과 hash
- 권고·심각도
- HITL 승인·반려·수정
- 알림 발송 결과
- latency, token, cost, error

LangGraph 상태 예시:

```text
question
user_id / organization_id
requested_project_id
project_candidates
resolved_project_id / routing_confidence
schema_version / prompt_version
cypher / validation_errors / correction_count
graph_result / document_evidence
recommendation / severity
approval_status
tool_trace / audit_run_id
final_answer / status
```

### 6.8 멀티페이지 데이터 플랫폼

P4의 화면 구성을 P3에 맞게 다음과 같이 차용한다.

- 대시보드
- 프로젝트·데이터 소스
- 적재 파이프라인
- 이상·품질 이벤트
- 승인 큐
- 관계·Graph Explorer
- 자연어 질의
- 평가
- 감사로그

### 6.9 판단 품질 평가

Cypher 정확도뿐 아니라 최종 분석·권고의 품질을 평가한다.

- 원인 후보의 데이터 근거 충분성
- SOP·매뉴얼 인용의 적절성
- 권고의 실행 가능성
- 위험 과소·과대평가
- 모르는 경우 보류했는가
- 도메인 전문가 승인·수정·반려율

### 6.10 이상감지 모델 결합(선택)

- 센서·품질 시계열이 있는 프로젝트에 한해 통계 또는 ML 이상감지 Tool을 연결한다.
- 이상 이벤트를 능동적으로 생성하고 Graph RCA와 문서 RAG를 후속 호출한다.
- P3 핵심 데이터가 이상감지 학습에 적합하지 않다면 억지로 포함하지 않는다.

## 7. 현재 구현 기준 진단

### 준비도 구분

| 범위 | 현재 판정 |
|---|---|
| P3 백엔드·데이터·평가 기반 | `READY` |
| P3 최종 사용자 서비스 | `NOT READY — PRODUCTIZATION GATE REOPENED` |
| P4 Agentic AI 기본 여정 병합 | `HOLD` |

### 구현된 기반

- `workflow.py`는 LangGraph `StateGraph` 기반이다.
- `project_id`와 `schema_context`가 파라미터화되어 프로젝트별 Agent를 생성할 수 있다.
- 프로젝트 Registry, 데이터 프로파일, 매핑 승인, 프로젝트 격리 적재,
  프로젝트별 schema context 주입 기반이 존재한다.
- 사용자가 사이드바에서 프로젝트를 수동 선택할 수 있다.
- 질의·데이터 적재·전문가 피드백 감사기록의 일부가 존재한다.

### 제품화 감사에서 확인된 문제

- `frontend/pages/`가 Streamlit 자동 멀티페이지 폴더로 인식되어
  `stSidebarNavItems`에 내부 모듈 파일명이 별도 메뉴로 노출된다.
- 자동 메뉴의 `projects`, `audit`, `dashboard` 등을 직접 열면 렌더 함수가
  호출되지 않아 HTTP 200이지만 본문이 없는 흰 화면이 나타난다.
- Streamlit 커스텀 작업공간 내비게이션과 자동 내비게이션이 동시에 존재한다.
- provider·model 선택, API 키·Gemini fallback 설명, Gold 회귀모드,
  역할 미리보기가 일반 사용자 UI에 노출된다.
- `p3-stage-badge`가 사용자 업무 상태가 아니라 개발 단계·foundation 상태를 표시한다.
- 긴 프로젝트명이 제한된 Streamlit 컨트롤에서 충분히 식별되지 않는다.
- React와 Streamlit이 동일·유사 기능을 서로 다른 메뉴·문구·레이아웃으로
  구현해 제품 정체성과 사용자 여정이 분산된다.
- 일부 화면은 한국어·영어가 혼합되고, 부분 번역이 언어 전환처럼 보인다.
- 기존 자동화는 HTTP 상태·예외·구조 크기·일부 지정 여정을 중심으로 검증해,
  자동 생성된 모든 내비게이션 링크와 의미 있는 본문 존재 여부를 놓쳤다.

### Agentic 목표에 아직 미달하는 부분

- 질문만으로 프로젝트를 선택하는 자동 라우터가 없다.
- Tool Registry와 표준 Tool 입출력·오류 계약이 없다.
- LangGraph Interrupt 기반의 영속 승인·재개가 없다.
- 문서 RAG, 권고 생성, 외부 알림이 통합되지 않았다.
- 질문→라우팅→Tool→Cypher→권고→승인→알림을 연결하는 통합 감사로그가 없다.
- 업로드·프로파일·매핑·적재·평가가 장시간 Job으로 연결되는
  영속 작업 큐와 취소·재개가 부족하다.
- 일부 확장 단계 문서가 README 진행 상태에서 한눈에 연결되지 않는다.
- `project_id` 정규식 검사만으로는 실제 멀티테넌시 보안을 보장할 수 없다.

## 9. 최종 완료 정의

최종 플랫폼 완료는 두 개의 순차 Gate로 판단한다.

### 9.1 P3 사용자 서비스 완료

1. React 제품 UI가 최종 사용자 단일 진입점으로 동작한다.
2. Streamlit 내부 콘솔의 자동 페이지 충돌과 중복 내비게이션이 없다.
3. production·demo 화면에서 개발·평가 기능과 내부 구현 설명이 격리된다.
4. 프로젝트 선택→질문→답변→결과표→관계 근거→저장·검토 여정이 완결된다.
5. 실제 사용자 기준 Release Gate를 통과한다.

### 9.2 Agentic 확장까지 포함한 최종 플랫폼

1. CiP-DMD가 아닌 두 번째 도메인 프로젝트를 만든다.
2. 새 파일을 업로드하거나 새 Neo4j를 연결한다.
3. 데이터 프로파일과 그래프 매핑을 검토·승인한다.
4. 적재 진행 상태와 무결성 검증을 실시간으로 확인한다.
5. 해당 도메인의 Gold 질문을 작성하고 평가를 실행한다.
6. 프로젝트를 직접 선택하면 그 프로젝트만 질의한다.
7. 프로젝트를 선택하지 않고 질문하면 LangGraph가 프로젝트를 라우팅한다.
8. 답변, Cypher, 결과표, 관계 경로, 문서 근거를 확인한다.
9. 위험한 권고는 승인 큐에서 승인·반려 후 재개한다.
10. 필요한 경우 알림을 발송한다.
11. 전체 과정이 하나의 감사로그에서 재현된다.
